# 同步通道加密协议（TSC/1）

> **设计前提**：后端要能直连公网（用户的 80 被 ISP 封、无证书、不想动 DNS），
> 而明文 HTTP 会让**登录口令与会话令牌**在链路上裸奔。
> 数据本身已是零知识密文，所以这里要保护的是**认证链路**。
>
> **本协议不发明任何密码学**：全部算法来自 Node 的 `crypto`（X25519 / Ed25519 / HKDF-SHA256 / AES-256-GCM），
> 本文件只规定**字节布局与状态机**。安全强度来自这些原语与下面几条纪律，
> 而不是来自"我们自研"这件事。

---

## 1. 目标与非目标

**目标**
- 传输加密：链路窃听者拿不到口令与令牌
- 服务端身份：客户端能确认"对面确实是我的服务器"（**钉扎**，无需 CA / 无需证书）
- 前向保密：长期密钥泄露**不能**解密历史会话
- 防重放与篡改：任何被改动/重放的帧都必须被拒

**非目标（明确不做，不要误以为有）**
- 不隐藏"谁在连这台服务器"（流量分析）
- 不防"首次连接就是中间人"——**首次连接是 TOFU**，必须靠**带外核对指纹**
- 不做 NAT 穿透/代理协商（那是上层的事）
- 不做证书吊销（钉扎的唯一恢复方式是用户手动更新指纹）

---

## 2. 算法与参数（全部固定，不做协商 → 天然免疫降级攻击）

| 用途 | 算法 |
|---|---|
| 密钥协商 | **X25519**（临时对临时，每连接新生成） |
| 服务端长期身份 | **Ed25519** |
| 密钥派生 | **HKDF-SHA256** |
| 对称加密 | **AES-256-GCM**（128-bit tag） |
| 随机数 | CSPRNG（`crypto.randomBytes`） |

**不做算法协商**：版本号固定为 1，不认识的版本直接断开。
（协商是降级攻击的温床；我们没有需要兼容的历史版本。）

---

## 3. 握手

### 3.1 `HELLO`（客户端 → 服务端，共 1+1+**2**+4+32+32 = **72** 字节）

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 1 | `magic` = `0x54`（'T'）——用于快速识别"这不是 HTTP" |
| 1 | 1 | `version` = `0x01` |
| 2 | 2 | `reserved` = 0 —— **非 0 一律断开**（不是忽略）。将来启用时用新的 magic/端口并存，见 §9 |
| 4 | 4 | `timestamp`（u32 BE，客户端当前秒）——**仅用于诊断日志**，不参与验签、也不做时钟偏移检查 |
| 8 | 32 | `client_random`（CSPRNG） |
| 40 | 32 | `client_eph_pub`（X25519 公钥） |

> **`timestamp` 不提供任何安全属性**：它既不防重放（防重放靠 `seq` 与每连接全新的
> `server_random`），也不做时间窗校验。**不要把它当成有时间窗防护。**

### 3.2 `SERVER_HELLO`（服务端 → 客户端，共 1+1+2+32+32+64 = 132 字节）

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 1 | `magic` = `0x54` |
| 1 | 1 | `version` = `0x01` |
| 2 | 2 | `reserved` = 0 |
| 4 | 32 | `server_random`（CSPRNG，**每连接全新**） |
| 36 | 32 | `server_eph_pub`（X25519 公钥） |
| 68 | 64 | `signature`（Ed25519，见下） |

### 3.3 转录与签名

```
transcript = HELLO_bytes || SERVER_HELLO_prefix(前 68 字节，即不含 signature)
signature  = Ed25519_sign(server_identity_privkey, SHA256("TSC/1 server-hello" || transcript))
```

客户端校验顺序（**任何一步失败都必须断开，不得降级到明文**）：

1. `magic`/`version`/`reserved` 合法
2. `server_eph_pub` 是合法 X25519 公钥（拒绝低阶点/全零——Node 的 `diffieHellman` 会返回全零共享密钥，**必须显式检查共享密钥非零**）
3. **用钉扎的 Ed25519 公钥验签**。未钉扎时进入 TOFU 流程（见 §5）
4. 计算会话密钥

### 3.4 会话密钥

```
shared        = X25519(eph_priv, peer_eph_pub)          // 32B，两侧相同
transcript_h  = SHA256(transcript)                       // 32B
                 // 两侧的 random 都参与 → 重放 ClientHello 也无法复用旧密钥
c2s_key       = HKDF-SHA256(ikm=shared, salt=transcript_h, info="TSC/1 c2s", L=32)
s2c_key       = HKDF-SHA256(ikm=shared, salt=transcript_h, info="TSC/1 s2c", L=32)
```

**双向各自独立密钥**：两个方向各自用计数器做 nonce，互不影响（否则同一密钥下 nonce 空间要共享，容易出错）。

临时私钥在派生完成后**立即从内存丢弃** → 前向保密。

## 4. 记录层（握手之后的所有字节）

每个方向是一条**有序帧流**：

```
[u32 BE length][u64 BE seq][12B nonce][ciphertext (明文长) || 16B GCM tag]
```

- `length` = `12 + 明文长度 + 16`（即 nonce+密文+tag 的总长），**上限 16 MiB**（超限立即断开，
  否则长度字段会成为内存耗尽的入口）
- `seq` 从 **0** 开始，**严格递增**；接收方要求 `seq == 期望值`，否则断开
  （防重放与乱序；TCP 本身有序，出现不等就意味着有人在动手脚）
- `nonce` = `[4 字节方向前缀][8 字节 seq]`
  - c2s 前缀 `00 00 00 01`，s2c 前缀 `00 00 00 02`
  - **同一密钥下 seq 不重复 → nonce 不重复**（GCM 的硬要求）。
    多出的方向前缀是第二道保险：即便实现出错把两个方向混用同一密钥，nonce 仍不会撞
- 明文 = 应用层消息（见 §6）

**为什么把 seq 放在 AAD 之外也安全**：它同时被 (a) 加密保护（GCM tag 覆盖 nonce 与密文）
与 (b) 明文递增校验约束；篡改 seq 会导致 nonce 不匹配 → tag 校验失败。

## 5. 钉扎（TOFU）与指纹

- 服务端首次启动生成 Ed25519 身份密钥对，私钥落在数据目录（`0700`，
  与同步数据同盘），**公钥指纹**方可公开
- 指纹 = `SHA256(pubkey)` 的 **32 位十六进制**（取前 16 字节），格式化为 8 组 4 字符便于口述核对
- **钉扎默认开启**。**"未钉扎就自动信任且不给用户看"是禁止的** ——
  TOFU 窗口期是唯一的中间人机会窗口，必须让用户有机会带外核对。
- 客户端首次连接：**未钉扎 → 必须显著提示用户核对指纹**（与 SSH 首次连主机同义），
  而不是静默接受。指纹格式化成 8 组 4 字符就是为了便于口述/抄写核对。
- 已钉扎且指纹**不一致** → **必须拒绝连接并显著告警**（可能被中间人），
  只允许用户在明确知情下手动更换指纹

> 这是 SSH 的信任模型。它的边界必须讲清：**首次连接可能已经是中间人**。
> 所以指纹要能通过另一条渠道核对（服务端日志/本机文件）。

## 6. 应用层消息

握手后，明文是长度无关的 JSON（由记录层定界），沿用现有 HTTP 端的请求/响应语义：

```json
{ "id": 1, "method": "login", "path": "/api/v1/login", "headers": { "authorization": "Bearer …" }, "body": { ... } }
{ "id": 1, "status": 200, "body": { ... }, "headers": { "retry-after": "60" } }
```

### 6.1 `headers` 是**白名单**，不是任意头
- **只允许 `authorization`**（Bearer 令牌）。服务端**必须**丢弃其余一切头 ——
  否则客户端能注入 `x-forwarded-for` 之类影响限流键的头，
  而限流正确性依赖于"这个头只能由反代提供"。
- 响应侧只允许 `retry-after`（见下）。
- 未列出的头**直接忽略**（不是报错），保证将来加头时旧实现不会把连接打断。

### 6.2 限流语义必须能在通道内传达
HTTP 端触发限流会回 `429` + `retry-after`；帧里没有独立位置，
所以把 `retry-after` 放进**响应 `headers`**。
**若不带它，客户端就不知道要等多久** —— 会立刻重试，等于自己放大攻击。
客户端在收到 `429` 时**必须**读该字段（缺省按 60 秒退避）。

- `id` 用于请求/响应配对（同一连接可并发多请求）
- `status` 复用 HTTP 语义（200/400/401/429…），**便于复用现有服务端路由逻辑与错误码**
- 这一层**不加密**（它已经在加密帧里）；它只负责把"请求-响应"映射到帧流

## 7. 必须写进测试的负例（这些比正例更重要）

1. **篡改任意一个字节** → 接收方必须断开（GCM tag 失败）
2. **重放一帧**（重复 seq）→ 必须断开
3. **打乱帧顺序** → 必须断开
4. **错误钉扎**（换一个 Ed25519 公钥签名）→ 客户端必须拒绝，**且不得继续发送任何应用数据**
5. **降级尝试**：版本号改成 2 → 双方都断开
6. **共享密钥为零**（低阶点攻击）→ 必须显式拒绝
7. **超长 length** → 断开而不是分配内存
8. **两端独立实现的互操作**：用固定测试向量保证服务端与客户端派生**同一会话密钥**
9. 前向保密：单独测试"长期私钥泄露不影响已派生密钥"（用已知向量断言会话密钥只依赖临时密钥）

## 8. 已知薄弱处（如实记录，含队友评审提出的）

- **能防被动窃听，但不防主动阻断**：攻击者可以在该端口冒充 HTTP 服务端或静默丢包。
  唯一的对策是 §3.3.1 的**硬性禁止 fallback** —— 客户端不能把"握手失败"退化成明文。
- **握手阶段没有速率/连接数限制**：记录层有帧长上限，但握手阶段没有；
  已建立连接数也无上限。公网暴露下这是 DoS 入口。**服务端应加**：
  单 IP 并发连接上限 + 握手超时。（store-dev 已修掉其中一半：
  **收到首字节即判 magic**，明文 HTTP 打进来 0.8ms 内断开，而不是挂到超时。）
- **`identity.key` 丢失后无恢复流程**：所有已钉扎的客户端都会校验失败。
  恢复方式只能是：重新下发新指纹给用户手动更新。**建议实现方提供"打印当前指纹"的命令**。
- **`length` 暴露明文长度**：能看出"登录请求比心跳长"。§1 已声明不防流量分析，
  所以这是**已知取舍**，但不要误以为有 padding。
- **无版本升级路径**：固定 v1、不协商是对的（避降级），但将来换算法只能
  **用新的 magic/端口与旧版并存**，不能做版本协商。

## 9. 尚需明确的风险（如实记录）

- **首次连接 TOFU**：见 §5 的边界
- **无流量分析防护**：链路观察者能看出"有人在同步、同步多频繁"
- **服务端需保存长期私钥**：私钥泄露 = 攻击者能冒充服务器（但**不能**解密历史会话，因为前向保密）
- **未做形式化验证**：这是工程实现，不是经过审计的协议。生产上更推荐 TLS；
  选择自研是为了满足"无证书、不动 DNS、直连端口"的约束
