# 性能目标（反超基准）

> 项目目标不是「功能对齐」，而是**在功能与性能上都超过参考实现**。
> 本文档定义可测量的指标与验收线，避免"感觉快了"这种主观判断。

## 参考实现的实测基线

以下数据来自对参考产品（XTerminal 5.8.6，Electron 应用）的实测，作为**必须超越**的底线。

| 指标 | 参考实现实测 | 我们的目标 |
|---|---|---|
| 安装包体积 | 133 MB（deb） | **≤ 100 MB** |
| 应用目录体积 | 396 MB（Installed-Size） | **≤ 300 MB** |
| 主进程 bundle | 1.1 MB（单文件，未分包） | 分包 + 懒加载，**首屏路径 ≤ 400 KB** |
| 渲染层资源 | 45 MB（含 i18n 3 MB 单文件 JSON） | 按需加载，**首屏 ≤ 2 MB** |
| 补全语料 | 15 MB / 768 个 spec 文件全量内嵌 | **按需加载 + 索引分离**，首屏不加载语料 |
| 冷启动到可交互 | 未精确测量（约 3-5s） | **≤ 2s** |
| 主进程空闲内存 | 未测量 | **≤ 150 MB** |
| 单 SSH 会话内存增量 | 未测量 | **≤ 25 MB** |
| 终端吞吐 | 未测量 | **≥ 10 MB/s**（`yes` 压测不卡 UI） |

## 实测结果（2026-11-07，本机 Xvfb 无头环境）

| 指标 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 冷启动到窗口可见 | ≤ 2s | **401 / 401 / 404 ms**（3 次） | ✅ 反超（参考约 3-5s） |
| 应用内 bootstrap（数据目录 → 窗口可见） | — | **178 ms** | ✅ 启动路径本身很轻 |
| 构建产物体积（main+preload+renderer） | — | **1.8 MB**（main 504KB / renderer 1.3MB / preload 4KB） | ✅ 对比参考 92 MB 的 app.asar，约 1/50 |
| 首屏入口 chunk | ≤ 400 KB | **390 KB** | ✅ 达标 |
| 补全语料 | 首屏不加载语料 | 索引 **15.4 KB**，明细 41.9 KB 惰性加载 | ✅ 对比参考 15 MB |
| 命令补全耗时 | ≤ 50 ms | **0.396 ms**（5000 条语料） | ✅ 大幅反超 |
| 主进程空闲内存 | ≤ 150 MB | **169 MB** | ❌ 略超 |
| 整机总内存（主 + GPU + 渲染 + 工具进程） | — | **621 MB** | ⚠️ 记录备查 |

### 内存未达标：原因与优化方向（诚实记录）
主进程 169 MB 超出 150 MB 目标。已定位的可优化点：
**13 个 IPC 域在启动时被一次性 import**（`src/main/ipc/index.ts`），
其中 ssh2 / better-sqlite3 / node-pty 等较重模块在启动阶段即被加载。

可行优化（按预期收益排序）：
1. **域级懒注册**：启动只注册核心域（app/store/ssh），其余首次使用时动态 register。
   预计能砍掉可观的主进程常驻内存，代价是路由表变成"按需装配"，需配套回归测试。
2. 重模块的顶层 import 改为首次调用时动态 `import()`（ai / mcp / monitor 最明显）。
3. GPU 进程 150 MB 属 Chromium 基线；可考虑按需启用 WebGL 而非默认开启。

**为什么先记录而不立刻改**：域级懒注册动到"路由装配"这一核心路径，
必须配一次完整回归；宁可如实标未达标，也不做半截改动让它看起来达标。

### 测量陷阱（踩过一次，务必避免）
若 Xvfb 没起来，Electron 会立刻以 `Missing X server` 退出，
而等待循环会跑满上限 —— 于是测出"恒定 10.5 秒"这种假数据（其实是轮询超时，不是启动耗时）。
**测量前必须确认进程真的起来了**（检查日志里没有 `Missing X server`），否则数字毫无意义。


## 关键性能设计（从架构上保证，而非事后优化）

### 1. 终端数据路径
- 主进程 → 渲染进程走 **二进制/字符串批处理 + 时间片合并**，避免每条 `data` 事件都触发 IPC
- 终端写入使用 xterm.js 的 **write callback 背压**，防止 PTY 高速输出打爆渲染层
- 大输出场景启用 **WebGL 渲染器**（`@xterm/addon-webgl`），失败时优雅回退 canvas
- 参考实现未做 IPC 合批，这是我们的主要反超点之一

### 2. 补全引擎
- 语料**不首屏加载**：manifest 索引（小）首屏加载，单个 spec 首次命中才读
- 语料解析结果做 **LRU 缓存**（上限可配）
- 候选计算放 **worker 线程**，避免阻塞主进程
- 输入**防抖**（可配，默认与你输入节奏匹配），并保证「打字流畅但候选及时」

### 3. 数据库
- better-sqlite3 **WAL 模式** + 预编译语句复用
- 批量写入用事务包裹
- 大表（会话日志、传输历史）分页查询，不全量载入内存

### 4. 文件传输
- 流式管道 + **可配置并发闸门**（默认 4，参考实现同值，但我们要做到可动态调整）
- 进度事件**节流**（默认 200ms，可配）
- 目录递归先**扫描后执行**，让用户看到总量与 ETA
- 大文件传输不占用主进程事件循环（异步流）

### 5. 监控采集
- 脚本**打包上传一次**，靠版本号比对决定是否更新（不重复上传）
- 采集结果**合并批量返回**，减少 SSH 往返
- **按卡片开关决定采集内容**（关掉的卡片不产生命令）
- 多会话采集**错峰调度**，避免同一时刻集中打满

### 6. 渲染层
- 长列表（连接数、进程数、传输队列）使用**虚拟滚动**
- 状态管理细粒度订阅，避免全树重渲染
- Monaco / xterm **懒加载**，未打开相关面板不加载
- 首屏只加载当前视图所需 chunk

### 7. 启动
- 主进程**延迟初始化**非关键服务（监控、同步、MCP 在首次使用时才起）
- 窗口 `show: false` + `ready-to-show` 再显示，避免白屏
- 预加载脚本保持精简（当前 < 1 KB）

## 测量方法（必须可复现）

```bash
# 冷启动耗时（无头，取 5 次中位数）
pnpm --filter @t1000/desktop build
for i in 1 2 3 4 5; do
  /usr/bin/time -f "%e" electron . --no-sandbox 2>&1 | tail -1
done

# 打包体积
pnpm --filter @t1000/desktop dist
du -h release/*.deb release/*.AppImage 2>/dev/null

# 主进程空闲内存（应用启动后静置 30s）
ps -o rss= -p $(pgrep -f 'electron .*--no-sandbox' | head -1) | awk '{printf "%.1f MB\n", $1/1024}'
```

## 打包实测（2026-11-08，electron-builder 25.1.8 / Electron 45.2.3 / linux-x64）

| 指标 | 目标 | 实测 | 结论 |
|---|---|---|---|
| **deb 安装包** | ≤ 100 MB | **92.6 MB** | ✅ 达成（参考实现 133 MB，小约 **30%**） |
| AppImage | ≤ 100 MB | **101.1 MB** | ⚠️ 差 1 MB（AppImage 压缩率不如 deb 的 xz） |
| **app.asar**（我们的代码 + 依赖） | — | **6.9 MB** | ✅ 对比参考实现的 92 MB，约 **1/13** |
| 应用载荷（asar + unpacked） | — | 约 43 MB | 其余为 Electron 运行时 |

### 体积是怎么降下来的（按收益排序）
1. **排除异平台原生二进制**（约 15 MB）：better-sqlite3 随包带了 8 个平台的 prebuild，
   Linux x64 只会用 `linux-x64.node`；node-pty 的 darwin/win32 同理。
2. **排除原生模块的 C/C++ 源码与编译中间产物**（约 18 MB）：
   better-sqlite3 的 `deps/` 与 `build/`（其中**没有** .node，运行期走 prebuilds）；
   而 node-pty / cpu-features 的 `build/Release/*.node` 是**必需**的，不能一起砍。
3. **`electronLanguages: [en-US, zh-CN]`**：Electron 自带 50+ 语言包。
4. **`compression: maximum`**：deb 走 xz 高压缩。
5. workspace 包 `@t1000/shared` 本就**完全内联**进 bundle（产物里 0 处运行时引用），
   从 dependencies 移到 devDependencies 并排除 —— 否则 electron-builder 会试图
   打包 `apps/desktop` 之外的真实路径并直接报错。

### 打包后必须验证原生模块（不能只看"打包成功"）
```bash
cat > /tmp/probe.cjs <<'EOF'
const D = require('<unpacked>/node_modules/better-sqlite3')
const db = new D(':memory:'); db.exec('CREATE TABLE t(a)'); db.prepare('INSERT INTO t VALUES (1)').run()
console.log('OK', db.prepare('SELECT a FROM t').get())
EOF
ELECTRON_RUN_AS_NODE=1 ./release/linux-unpacked/terminal-1000 /tmp/probe.cjs
# → BETTER_SQLITE3_OK {"a":1} / NODE_PTY_OK true
```
`ELECTRON_RUN_AS_NODE=1` 是关键：它用 **Electron 的 ABI** 跑脚本，
测的才是"打包产物里的 .node 能不能被 Electron 加载"；用宿主 node 测会因 ABI 不同而假失败。

另外做了对照实验：打包版与未打包版用全新 profile 启动都不会立刻生成 `local-store.db`
→ 属应用自身的懒初始化行为，不是打包回归。**对照实验很便宜，但能直接把
"我改坏了"和"本来就这样"分开。**

## 主进程内存：目标本身定错了（2026-11-08 用对照实验纠正）

原目标「主进程空闲内存 ≤ 150 MB」。实测 169 MB → 懒加载优化后 162 MB，仍未达标。
于是跑了一个**不含任何我们代码**的最小 Electron 应用（同版本、同环境）作对照：

| 对象 | 主进程 RSS |
|---|---|
| **裸 Electron 45.2.3**（只开一个空白窗口） | **150 MB** |
| terminal-1000（18 个域、完整界面） | **162 MB** |
| **差值 = 我们的代码实际占用** | **约 12 MB** |

结论：**150 MB 就是 Electron 自身的地板**。在 Electron 45 上任何应用都到不了它 ——
这不是可达成的工程目标，而是把宿主的固定开销当成了自己的预算。

**该看的数字是那 12 MB**：18 个 IPC 域、加密存储、SSH/SFTP/VNC/RDP/Telnet 各协议实现、
补全引擎、AI/MCP/广播，加起来约 12 MB；其余约 150 MB 是 Chromium/Electron 运行时。

### 教训：定内存目标前先量宿主基线
不量基线就会陷入"优化到 150MB 以下"的死胡同，而那个数字根本不含我们的代码。
**正确做法**：先测同版本宿主的空载占用，再把预算定在「基线 + 我们的合理增量」上。

### 仍做了的优化：IPC 域懒加载
18 个域原先启动时全部 import；现改为**首次调用才 import**
（`router.registerLazyDomain`），只有 `app` 立即注册；关停路径也改为动态 import，
否则静态 import 会把懒加载彻底抵消。

实测只省约 7 MB —— 因为渲染层启动即调用 `store`/`settings`，
而它们会拉起 better-sqlite3，这是**设计上就该有**的依赖。

懒加载仍然保留，因为架构上是对的：**没被用到的域（AI/MCP/VNC/RDP…）
不该为它的存在付启动内存与启动时间**；收益在"用户从不打开那些功能"的会话里体现。

> 动态 import 用于关停路径是安全的：**模块已加载时走缓存、瞬时完成；
> 模块从未加载，说明这次会话没建立过对应资源，也就没有什么要清理。**
